# 生存战争挖矿/工具机制备忘(源码实测)

> 2026-08-06,反编译源码(~/sc-src)全量核查:公式 ComponentMiner.cs,数值 Assets/BlocksData.txt,
> 矿层 TerrainContentsGenerator*.cs,配方 CraftingRecipes.xml。知识指南"挖矿与工具(引擎实测).md"的数据来源。

## 1. 挖掘公式

`耗时 = 方块DigResilience / (工具对应Power × StrengthFactor)`,按 0.25s 的"戳击"节拍取整。

- 方块有挖法类别(Shovel/Quarry/Hack),只取工具**对应类别**的力值——用错类别惩罚巨大
  (铁镐 Hack 只有 1.5:砍树 3.3s;铁斧 Quarry 1.5:挖铁矿 14.7s)。
- 徒手三力全为 1,ToolLevel=1。StrengthFactor:等级/性别/体力/疾病,约 0.4~2.0(21 级翻倍)。
- 无穷大 = 液体(无挖法)和基岩(抗性∞)。生存模式挖掘距离 5 格。NPC 走 `Miner.CalculateDigTime` 同一公式。

## 2. 关键真相:掉落无工具门槛

`Block.GetDropValues` 唯一的门是 `toolLevel < RequiredToolLevel`,而**全部 7 种矿的 RequiredToolLevel=0**
(BlocksData 第 37 列逐行核对)。**徒手挖钻石矿掉满 2 钻石+3 经验珠。**
游戏内置帮助《开采》里"钻石或孔雀石需要更好的工具,否则将不会得到任何东西"是**旧版遗留错误文案**。
全游戏唯一 >0 的方块:GrassTrapBlock(草陷阱,需 ToolLevel≥3=铜级)。雪/树叶=1(徒手即满足)。

## 8. 找矿半径的物理上限(为什么 find_blocks 封顶 64)

**世界不是全都在内存里。** `TerrainUpdater` 按"更新位置"分配和释放区块:

- `PrepareForDrawing(camera)` → `SetUpdateLocation(playerIndex, 相机XZ, VisibilityRange, **64f**)`
  ——每个玩家周围 **64 格**的区块保有"内容"(`TerrainChunkState.InvalidVertices1`:方块数据、光照、
  方块行为、生物刷新——模拟需要的一切,只是不生成渲染网格)。
- `AllocateAndFreeChunks` 会把**不在任何更新位置范围内的区块直接 Free 掉**(先存盘)。

所以 `terrain.GetChunkAtCell(x, z)` 在 64 格外返回 null,`GetCellValue` 一律返回 0(空气)。
**搜索半径开再大也只是在读不存在的地形**,这就是 find_blocks 封顶 64 的原因,不是偷懒。

守护灵有**自己的**区块气泡(`GeniusExpeditionKeeper`),半径 `LoadRadius` = **48**,
用 `SetUpdateLocation(idx, xz, 0f, LoadRadius)` ——可见距离传 0,只要内容不要渲染网格,
这正是引擎自己给无相机玩家用的姿势 `PlayerData:265`。要搜更远只能走过去或传送过去。

**这个气泡是无条件常开的**,不跟"远征模式"绑定(v0.9.6 修)。原来只在离玩家 >40 格时才注册,
于是站在离玩家 30 格的地方时守护灵没有自己的气泡,只能蹭玩家那个——而玩家的气泡是**以玩家为中心**的,
背离玩家那一侧的地形只到 64-30=34 格,更大的 find_blocks 半径在那个方向被悄悄截断。
靠近玩家时两个气泡大面积重叠,常开的边际成本很小,换来的是守护灵各个方向视野一致。

远征模式(刷生物 + 防清除)仍然按距离开关——那部分靠近玩家时会和引擎自己的工作重复。

区块内存代价:`TerrainChunk.Cells = new int[65536]` = **256 KB/区块**。
半径 48 ≈ 50 个区块 ≈ 13 MB;半径 64 ≈ 79 个 ≈ 20 MB;半径 128 ≈ 254 个 ≈ 65 MB(平方增长)。
这是把守护灵气泡定在 48、上限定在 64 的实际理由。

### 扫描性能(1024 上限与列内连续)

- `Terrain.ExtractContents` = `value & 0x3FF`,`BlocksManager.m_blocks` 正好是 `Block[1024]`
  ——所以"这个方块匹配吗"可以用 `byte[1024]` 查表,而不是字典。地下几乎每格都是实体方块,
  这条是热路径,字典探测比读地形本身还贵。
- `TerrainChunk.Cells[y + x*256 + z*4096]`:**Y 在内存里是连续的**。
  按列取一次区块再纵向走,比每格 `GetCellValue`(每格一次区块查找)快一个量级。
- find_blocks 按**同心方环由近及远**扫,并有单次调用的读格预算:即使中途停下,
  拿到的也一定是最近的那些,还能如实报告"实际搜到了多少米"。

## 9. 挖梯井:身体是两格高的(descend_to 的硬约束)

`Assets/Database.xml` 里人形生物的 `BoxSize` 是 **`0.5,1.77,0.5`**,
`ComponentBody` 的碰撞盒从脚下那格向上量 1.77 格,所以身体永远**同时占两格**:
脚格 `y` 和头格 `y+1`(`StanceBoxSize` 只在蹲下时把 Y 压到 0.4 倍)。

梯井每一步是"横移一格 + 下降一格"。横移发生在**下落之前**,
也就是说身体会先以**当前高度**进入目标那一列,然后才掉下去。
于是目标列必须挖空**三格**(相对落脚格 `t`):

| 相对高度 | 是什么 | 不挖会怎样 |
|---|---|---|
| `t+2` | 横移途中的**头格** | 头卡在岩石里,走不过去 |
| `t+1` | 横移途中的脚格 | 脚卡住 |
| `t+0` | 落脚格 | 无处可落 |

**v0.9.5 只挖了 `t+1` 和 `t+0`**,漏掉头格。后果不是"偶尔失败"而是"在实心岩层里必然失败":
playtest 7 的 `Game.log` 里 8 次 `descend_to` 全部返回
`could not step down into the shaft`,挖到的层数是 0/0/0/2/3/3/3/3
——那几层全是地表附近碰巧本来就是空气的地方。

顺序也有讲究:**从上往下挖**。沙子和沙砾一旦失去支撑就会下落,
先挖脚格会被上面塌下来的方块重新填上。

几何规则抽到了 `GeniusDescentGeometry`(不依赖引擎类型),
`DescentGeometryTests` 用一个"全是实心岩石"的模拟世界跑 60 层,
断言身体每一步都不会嵌进实体格——把 `CarveHeights` 改回两格,这个测试立刻红。

### 水里不能挖竖井

`ComponentBody.ImmersionFluidBlock` 是 `WaterBlock` 时直接拒绝:泡在海里时四周全是水,
危险检查只会永远报"下面是水",而模型看不出该怎么办(playtest 7 里它用同样的参数重试了两次)。
错误信息要写明**下一步**(先上岸),不能只写"我停下了"。

## 10. 传送必须能直达矿层

原来的落点规则是"目标格已经是空气、且脚下 3 格内有实地才保留,否则贴回地表"。
矿带在 y2-40 的实心岩里,于是 `teleport(x, 38, z)` **永远**返回 y=76 —— 地下坐标一律作废。

playtest 8 里守护灵自己把这条总结出来了:

> ②传送地下坐标会落到地表,不能直达矿层

现在按请求的 y 落地:

| 目标格状况 | 处理 |
|---|---|
| 已是可站立的空腔 | 直接落 |
| 附近 ±6 格内有空腔 | 落到最近的那个,并说明改了 y |
| 实心岩层 | **就地开一个两格高的容身洞**(`SubsystemTerrain.ChangeCell`) |
| 半空(下方没有落脚点) | 沿目标 y **向下**找第一块实地,而不是弹回地表 |

只保留三条真正关乎安全/礼貌的拒绝:目标 3×4×3 范围内有岩浆、
要开的两格是玩家搭的方块(`GeniusProtectedBlocks`)、下方彻底没有落脚点。

区块没加载时的悬停落地同样带着目标 y(`PendingTeleportTarget`),
否则"等加载完再落"会把 y 悄悄丢掉,又变回贴地表。

### 玩家建筑保护从提示词变成代码

"绝不拆玩家的建筑"过去只写在 system prompt 里,模型愿不愿遵守全凭自觉。
`GeniusProtectedBlocks.IsPlayerBuilt` 把它落到代码:箱子/熔炉/工作台/火把/木板/梯子/门/
玻璃/砖/楼梯/栅栏/告示牌 —— 只列**地形生成器绝不会放**的方块,
所以天然石头、泥土、沙子、矿石一律照挖。宁可漏判(顶多绕一下),不可误判(会拆房子)。

### 沙子会灌回竖井

playtest 8:`沙子 is still blocking (22,72,20)`,同一处两次。挖开 ≠ 挖开了还在开着。
现在每一 tick 重新检查那三格,塌回来就退回挖掘状态继续挖,**同一格最多重挖 8 次**;
超了就如实说"上面是一整根沙柱",让模型横向挪 8-10 格再下潜。

注意重挖必须挖**同一列**:`_directionIndex` 在开始走的时候就 +1 了,
按它重算方向会转到下一个方向去,留下一个挖了一半的楼梯。

## 11. 区块"存在"不等于地形"生成了"——这条弄死过守护灵

`Terrain.GetChunkAtCell` 一旦区块被**分配**就返回对象,而生成器还没填内容。
在那之前每个格子读出来都是 0(空气),`GetTopHeight` 返回 0。只做 null 判断的代码
于是看到的是"已加载,而且全是空气"。

playtest 11 的死法:

```
17:30:16  teleport {"x":-41,"y":110,"z":313}
       -> "区域还在加载,我先安全悬停,几秒内落下"
17:30:23  ⚰ Genius 阵亡于 (-41,1,313),压死
```

悬停解除时看到一个刚分配的空区块 → `GetTopHeight` = 0 → 把身体放到 y≈1 →
七秒后生成器在它周围把地形填了出来 → 压死。

引擎自己的判据是 `State >= TerrainChunkState.InvalidLight`:`ComponentIntro.cs:148`
在给玩家选出生点、要读格子之前用的就是这个。低于它意味着四趟内容生成还没跑完。

统一收进 `GeniusTerrainReady`,仓库里**所有** 8 处 `GetChunkAtCell` 判断都改用它——
不只是传送,扫描的"世界到 Nm 就没了"、导航的起点检查、远征守护都吃同一个错。
这大概率也解释了此前几次"扫描空空如也"。

另外补了个兜底:悬停超过 25 秒仍未生成,就**回到出发点**并报
`error[area_not_loaded]`,而不是永远挂在天上——那会让之后每个指令都作用在一个不存在的身体上。
